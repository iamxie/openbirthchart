# 完全基準：四項差異診斷與角度最大值

2026-10-31。讀取封存的產品 v0.6.5／Swiss 2.10.03 原始結果，另直接呼叫兩套公開 API 探測宮頭及鄰域；沒有修改計算、依賴或基準。
日期時間均為表列城市的當地時間。宮位座標不是黃經角度，不能將兩者的殘差混為角秒。

Lib 的迭代追蹤：精確 ASC 的地平線符號測試僅約 +1.11e-16～+5.55e-16，走「地平線上方」分支；ASC 增加極小黃經後切到另一分支。三個嚴重案例的迭代皆在 21～22 步、內部緯度殘差小於 1e-6 度時停止，卻回傳與第一宮頭不銜接的宮位座標。這定位到分支／迭代回傳的邊界一致性問題，並非 ASC 的天文黃經差了半宮；尚未獨立裁定完整 Polich–Page 幾何定義或修復方法。
Swiss 精確 ASC 回傳 1.0，極近鄰也回 1.0；但 −1e-6 度即可回到相同的 12.17／12.57／12.55。不能把只硬設 ASC=1 當作鄰域演算法已修好。

## 2. 六十六個 Azimuth MC

66／66 的 MC 與產品第十宮頭精確相等；Lib／產品給第 4 宮，Swiss 在精確 MC 給第 10 宮。黃緯全為 0，不能以一般天體的非零黃緯解釋。
桌面以實際 cusps 畫宮頭，以 chart.mc 畫 MC，故依現有繪圖路徑會呈現「MC 在第十宮頭，表格第 4 宮」。這是數據及繪圖程式核對，沒有宣稱逐張打開 66 個 GUI 驗收。
其中 60 張為南半球正向宮頭、6 張為北半球反向宮頭（Manila 5、Bangkok 1）；不能說成全是南半球。64 點原始值未補正、2 點使用現有 3.999…→4 尾數補正。
代表案例 complete-1904-01-H：Swiss 在 MC−1e-6° 回傳 4.000000139496788，精確 MC 為 10.0，MC＋1e-6° 為 3.9999998790217344。這再次呈現精確宮頭標號與鄰域連續公式的分歧。
66 是本樣本「產品／Swiss MC 不同」的數量，不是全部 Azimuth 內部編號不一致的完整影響範圍。

**8 個 C／R：宮頭完整反向排列，但被目前產品只容許 H 反向的規則擋下。** 直接重算 `house_direction` 為 −1，反向宮寬合計為 360°。所以不是 Lib 沒有算出十二宮頭，也不是資料缺少；是 `ChartEngine.calculate` 的非 H 反向檢查拒絕。
**5 個 T：宮頭黃經順序交錯，正向合計 1080°、反向合計 3240°，兩個方向都不是一圈。** 先在 `house_direction` 被拒絕；僅開放反向白名單無法處理。
以 1941-07 的 T 為例，第 1～4 宮頭約為 356.177°→261.654°→263.911°→270.545°，先減再增；現有「每個相鄰宮頭形成單向扇區」模型不成立。Swiss 仍提供宮頭及歸宮值，但不代表現有二維扇區畫法可以直接套用。
相同 ARMC／地理緯度／黃赤交角下，兩套 API 的這 13 組宮頭最大差僅 2.864908310584724e-9 角秒；兩者對宮頭位置幾乎一致。以各自獨立時角／黃赤交角比較，最大差為 0.01765113137253138 角秒。這裡是補充探測，不併入原來只有雙方成功 1979 張的統計。
因此要分開看：C／R 是現有產品支援限制；T 是宮頭排列與現有圖面／有效性條件不相容。都不能直接稱為「高緯度無解」。

## 證據

- selected.json：原基準的具名案例節錄；polich-cases.json、azimuth-66.json：軸點及宮頭身分核對。
- lib-probes.json：直接 Lib 宮頭／鄰域實算與迭代追蹤；swiss-probes.json：獨立 Swiss 2.10.03 公開 API 鄰域與相同參數測試。
- angle-maxima.json：每個天體／宮頭的黃經、黃緯、球面角距最大值與完整案例。
- baseline-hashes-before.json／preservation-check.json：兩份基準全檔雜湊未變；Lib 探測無 guard 事件。
- [Swiss API 官方說明](https://www.astro.com/swisseph/swephprg.htm)：house_pos 使用實際黃經／黃緯，回傳帶有宮內位置的小數宮位座標。官方文件不能取代本次版本固定 API 探測。
