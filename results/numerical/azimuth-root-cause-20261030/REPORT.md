# Azimuth 差異根因診斷（不修改計算或基準）

日期：2026-10-30。產品 0.6.2／LibEphemeris 3.2.2，參考 Swiss Ephemeris 2.10.03。

## 結論

本輪 58／101 張 Azimuth 的零黃緯歸宮差異，已定位為「宮頭 API 與 house_pos API 採用的宮號方向／起點不一致」。這種不一致可在 Swiss 自身重現，LibEphemeris 的對應 API 也存在；不是本程式把宮頭區間讀錯，不是行星星曆精度、時間換算或隨機浮點漂移造成。

我們的產品使用 LibEphemeris 計算宮頭，再自行以有向黃經區間歸宮，**沒有呼叫 LibEphemeris.house_pos**。本次確認這個產品政策的執行與宮頭編號一致；不代表替所有占星傳統裁定唯一正確的 Azimuth 編號方式。若以固定正東起算的空間方位角作定義，則必須重新協調宮頭、宮號與落宮整套規則，不能只換掉歸宮函式。

## 三層責任區分

| 層次 | 實測 | 判定 |
| --- | --- | --- |
| LibEphemeris 宮頭 vs Swiss 宮頭 | 同 ARMC／緯度／黃赤交角，101 張最大差 4.9112713895738125e-9 角秒 | 不是兩家宮頭算出明顯不同位置 |
| 產品歸宮 vs 同一組 Lib 宮頭區間 | 2020 個點全部一致 | 未發現本程式讀反方向或排錯宮號 |
| Swiss 的宮頭 vs Swiss.house_pos | 58 張在同一 API 家族內不一致，宮頭鄰域發生非正常跨宮跳躍 | 已證實內部一致性缺陷；尚未取得維護者對修復方向的確認 |
| Lib 宮頭 vs Lib.house_pos | 同樣使用有半球／方向差別的宮頭，但 house_pos 連續公式按固定方位角編號 | 同類型的 API 編號不一致；目前產品未使用此函式 |

## 根因如何發生

以「正東為 0°，朝正北增加」的方位角記為 α。這只是本診斷清楚定義的座標，不是宣稱所有占星傳統必須如此。

本輪獨立笛卡兒座標計算顯示，兩套庫的宮頭實際採用：

| 條件 | 第一宮頭方位 | 從第一到第二宮頭的方位角步進 | 案例數 | 與 Swiss.house_pos 不同張數 |
| --- | --- | --- | ---: | ---: |
| 北半球，黃經正向排列 | 正東 α=0° | +30° | 43 | 0 |
| 南半球，黃經正向排列 | 正東 α=0° | −30° | 42 | 42 |
| 北半球，黃經反向排列 | 正西 α=180° | +30° | 6 | 6 |
| 南半球，黃經反向排列 | 正西 α=180° | −30° | 10 | 10 |

這裡「黃經正／反向」與「方位角增加／減少」是兩件事。原 16 張反向案例包含北半球 6 張、南半球 10 張，不能把所有問題概括成南半球。

Swiss.house_pos 的 H 連續公式卻總是按固定的 α/30+1 編號，沒有套用上述南半球的方向變更及反向案例的起點變更。Lib.house_pos 的連續輸出同樣如此。它們算的方位角本身可由獨立三維向量計算重現；問題是該方位角的宮號與各自宮頭表的宮號不一致。

Swiss 另有通用的宮頭捷徑：黃緯為零且距某宮頭小於 0.001 角秒時，直接回傳該宮頭編號。因此「剛好在宮頭」看似正確，離開這個極小範圍，才會暴露兩套編號的矛盾。Lib 本輪直接 API 沒有相同的宮頭捷徑，不應把 Swiss 的跳躍機制也歸給 Lib。

## 完全不經本程式即可重現

不需要出生時間、時區或星曆檔；固定 ARMC=90°、地理緯度=+12°、黃赤交角=23.4393°：

- Swiss.houses_armc(H) 回傳第一宮頭黃經 0°。
- Swiss.house_pos(H, 黃經 0°、黃緯 0°) 回傳 **1**。
- 黃經改成 359.999°：回傳 **7.000006620**。
- 黃經改成 0.001°：回傳 **6.999993398**。

這是第 1 宮頭兩側突然落在第 7 宮交界附近，不是正常的第 12／1 宮銜接。獨立幾何確認這個點在正西、水平投影長度為 1，沒有接近天頂／天底的方位角奇點。

另以 ARMC=0°、緯度=−30° 的正常順序盤測第二宮頭：精確宮頭回傳 2，兩側卻約為 12.000055280 與 11.999944737。北半球正向對照則正常。

可獨立提供給維護者的最小重現程式：[minimal_swiss_repro.py](minimal_swiss_repro.py)，實際輸出：[minimal-swiss-output.json](minimal-swiss-output.json)。尚未向任何外部維護者發送訊息。

## 驗證範圍與數量

- 全部 101 張 H：85 張主案例＋16 張補充；共 2020 個點、1212 個宮頭。
- 每宮頭取 −0.001、−0.000001、−0.00000001、0、+0.00000001、+0.000001、+0.001 度，共 8484 次鄰域探測。58 張盤共 592 個宮頭出現超過半宮的局部跳躍。
- 以黃道單位向量轉赤道，再與當地東／北／上向量內積，獨立算出方位角。1919 個距宮頭超過 1e-6 度的點，套用由宮頭定義導出的方向／起點後，宮號與產品全部一致。其餘 101 個宮頭附近點另外檢查，不拿微小邊界誤差推論編號問題。
- Lib 與獨立幾何：零黃緯非邊界點最大差 7.389644451905042e-13 度；實際黃緯所有點最大差 7.73070496506989e-12 度。
- Swiss 與 Lib 連續零黃緯輸出的固定微差約為 2.77778e-7 度，即 Swiss 加入的 0.001 角秒邊界偏移；與跨數宮的差異尺度完全不同。
- 額外固定網格：緯度 ±0.1°、±12°、±40°、±70°；ARMC 每 15°一組，共 192 組。每組 72 個黃經測點，共 13824 點；納入同一方向／起點規則後全部吻合。這是診斷規則，未寫入產品。
- 五個點若拿「稍有末位差距的 Swiss 宮頭」直接判區間，會出現額外的宮頭邊界差異；換回產品真正使用的 Lib 宮頭後，2020 點差異為零。未將此測試方法差異誤判成新 bug。
- 本輪主要追查零黃緯差異；原本含實際黃緯的空間歸宮與黃經區間政策之差異仍是另一題，未改變產品定義。沒有宣稱已涵蓋赤道、兩極及全部退化幾何條件。

## 原始碼與官方文件交叉核對

已查閱 [Swiss v2.10.03 swehouse.c](https://github.com/aloistr/swisseph/blob/v2.10.03/swehouse.c) 的 H 宮頭分支、house_pos 入口及 H 分支，分別解釋實測的半球／起點差異及捷徑。下載快照保留完整原授權；只存在此診斷資料夾，沒有放進 vendor、產品或封裝。亦檢視當日 master 的相同分支，相關行為仍存在於原始碼；**未編譯或實跑 master**，不把來源閱讀說成新版實測。

[Swiss 官方一般文件](https://www.astro.com/swisseph/swisseph.htm) 6.2.9 將第一宮頭描述為正東，6.4 對熱帶特殊情況又有不同方向描述；不能只靠一段簡述決定哪一個 API 應改。[程式介面文件](https://www.astro.com/swisseph/swephprg.htm) §14 說明 house_pos 包含空間幾何落宮。此次將黃緯固定為零仍重現差異，因此不能用「一個有黃緯、一個沒有」解釋這 58 張。

本機實際 LibEphemeris `houses.py` 路徑與雜湊記於 [lib-manifest.json](lib-manifest.json)；直接 API 測試使用產品 Python 環境並啟用既有 guard，未載入 Swiss。Swiss 測試則使用獨立 Python 3.11 環境。沒有修改任何套件。

## 後續建議

先保留產品現有的「以所顯示宮頭編號歸宮」政策，將本次最小案例留作上游問題證據。不要為了追平 house_pos 就把 58 張盤的宮號直接覆寫；這會讓表格宮號與圖上的宮頭區間不一致。

若後續決定採用固定正東的空間方位角編號，需明確批准新的 Azimuth 定義，協調宮頭、歸宮、圖表及說明，再另建新基準。這是政策／相容性決策，不是本次已授權的修復。

本輪只有診斷程式、輸出及文件。0.6.0／0.6.1／0.6.2 基準、產品程式、依賴與已交付 ZIP 保持原樣；保護雜湊及證據雜湊見 `final-verification.json`。
